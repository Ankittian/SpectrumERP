# Plan: SpectrumERP Knowledge Graph pipeline on EC2

Status: proposal, nothing in this plan has been executed. Items marked **[verify]** were not confirmed against the code or a
live system and must be checked before relying on them.

Goal: after this is done, a **new phase** is added by committing its code to Git and running one command
(`kgpipe run --phase N`). The pipeline parses the code, finds nested stored procedures, generates the functional YAML for
review, builds the embedding texts and **updates** the existing Neo4j graph (running in Docker on EC2). An MCP server over
that graph is reachable from the LAN over the existing VPN.

Related documents: `README.md` (setup), `GRAPH_STRUCTURE.md` (spec), `PLAN-live-code-and-incremental-kg.md` (earlier
proposal for Git-backed code and incremental load; this plan builds on it and supersedes its open decisions).

## 0. Decisions already taken

These are fixed. Everything below follows from them.

### 0.1 Git repository references (nodes link to Git, not to a local directory)

| # | Decision |
|---|---|
| D1 | Source code lives in a **private GitHub repo**. The repo **keeps the phase folders**: `graphs-by-phase/phase-N/phase-N/<FormName>/...`. |
| D2 | Every code-bearing node stores a **repo-root-relative path** and a **permalink URL pinned to a commit SHA**. Never a branch, because line anchors drift. |
| D3 | Permalink format (GitHub): `https://github.com/<org>/<repo>/blob/<sha>/<path>#L<start>-L<end>`. Host differences live in one module (`provenance.py`), so another host later changes only that module. |
| D4 | `KGMeta` records `repo`, `branch`, `commit` for each load. |
| D5 | The old graph stores paths such as `phase-0/phase-0/fMaterialGroup/Form/fMaterialGroup.vb` (no `graphs-by-phase/` prefix) and nested SP paths such as `embedding_text/X.txt`. After the move every path is rewritten to its real repo path. There is no in-place migration of the old Aura data: phases 0 and 1 are **rebuilt** from source (section 4), which rewrites all paths. |
| D6 | The `code` property stays on nodes for now (search and embeddings use it). Only `file`, `source_files`, line numbers and the new URLs change. Embedding text must **not** contain paths or URLs, so a new commit does not invalidate every embedding **[verify in `embed.py`]**. |
| D7 | Shared nodes (e.g. `usercontrol:QCGroup`, 14 files in 7 bundles) keep **one URL per file copy** (`source_urls`), not one merged link. |
| D8 | Stub SPs with no source (15 in the live graph) get **no URL** and `source_kind = "missing"`. |

### 0.2 Nested stored procedures

| # | Decision |
|---|---|
| N1 | A **nested SP** is an SP that is `EXEC`'d by a bundle SP (or by another nested SP) but has no `.sql` file in any form bundle. |
| N2 | Detection is **deterministic**: sqlglot over bundle SP code, recursing to a depth cap of 8. **No LLM** is involved in finding or fetching them. |
| N3 | Their code comes from an **exported SP folder committed to the repo** (`sp-export/`, files named `Schema.ProcName.sql`). EC2 has no database connection. |
| N4 | Nested SPs are resolved **before** YAML generation, so the graph the LLM is grounded in has complete SP chains. |
| N5 | Nested SPs get **no YAML of their own**. They become `StoredProcedure` nodes from SQL. The functional YAML only references them (a rule's `implemented_by: sp:...`, or tables a concept stores). |
| N6 | The Git link of a nested SP points at the real `.sql` in `sp-export/`. The old `.txt` embedding-text wrappers (197 files) are no longer needed as input, because the build regenerates the header from parsed SQL. |
| N7 | Dynamic calls (`EXEC @var`, `EXEC(@sql)`), unresolved names and SPs missing from the export are **reported, never guessed**. |

### 0.3 Other decisions

| # | Decision |
|---|---|
| P1 | Which forms belong to a phase is defined in **`phases.yaml` in the repo**, edited by hand. |
| P2 | Functional YAML (modules, concepts, rules, processes, form docs) is generated by the **Claude API** for new forms only, grounded in the extracted graph, and goes through a **pull request in the repo** before it can reach the graph. Merge = approval. |
| P3 | Neo4j **Community 5.x in Docker Engine** on EC2 (not Docker Desktop), bound to localhost. |
| P4 | Embeddings stay **local Qwen3-Embedding-0.6B, 1024 dimensions**, the same as the existing graph. The model is frozen for the life of the graph. |
| P5 | The MCP server runs on the same instance over HTTP with a bearer token, reachable only through the **existing VPN**. |
| P6 | The pipeline is a **local CLI first** (`kgpipe`), run by hand or cron. A push-triggered run is a later wrapper. |
| P7 | The pipeline **updates** the graph; it never does a blind full reload against the live database. |

## 1. Architecture

```
                 GitHub (private)
  graphs-by-phase/phase-N/phase-N/<Form>/...   sp-export/*.sql   phases.yaml   domain/
                       │
                       ▼  git fetch at a pinned commit
 ┌───────────────────────────── EC2 (Ubuntu 24.04) ───────────────────────────────┐
 │  kgpipe  ──►  fetch → phases → parse → nested-sps → build graph.json            │
 │                       → gen-domain (Claude API) → PR → [human merge]            │
 │                       → validate → embed (Qwen3 local) → diff-load → verify     │
 │                                                                                 │
 │  Neo4j container (127.0.0.1:7687, data on EBS /data)                            │
 │  spectrum-kg MCP server (systemd, :8765, bearer token)  ◄── VPN ── LAN clients  │
 └─────────────────────────────────────────────────────────────────────────────────┘
        │ outbound only: GitHub, Anthropic API, Hugging Face (model download once)
```

Layers and what builds them (verified from `build.py`, `extract/bundle.py`):

| Layer | Source | Builder |
|---|---|---|
| Code: Form, UserControl, Control, FormMethod, DT*/DA* | `.vb` / `.cs` in bundles | Roslyn (`extract/code.py`) |
| Data: StoredProcedure, Table, Column | bundle `.sql` + nested SP SQL | sqlglot (`extract/tsql.py`, `link.py`) |
| Functional: Module, BusinessProcess, BusinessConcept, BusinessRule, form/control docs | `domain/*.yaml` | `domain.py` |

Table and Column nodes exist only because SP SQL mentions them. There is no schema export. A table reached only through
dynamic SQL, or an SP missing from the export, has no node.

## 3. EC2 infrastructure setup (M1)

### 3.1 Instance
1. Ubuntu 24.04 LTS, `m6i.xlarge` (4 vCPU, 16 GB RAM), 30 GB root volume.
2. Second EBS volume (gp3, 100 GB) for `/data` (Neo4j data, backups, `.cache/`). Enable EBS encryption.
3. IAM instance role with: read on the Secrets Manager secrets used here, write on the backup S3 prefix, CloudWatch Logs
   write. No admin rights.
4. Security group: inbound SSH from the admin IP only. Port 8765 is opened to the VPN CIDR in step 3.7, not before.
5. Time sync and unattended security updates on.

### 3.2 Mount the data volume
```bash
lsblk                                    # find the new device, e.g. nvme1n1
sudo mkfs.ext4 /dev/nvme1n1
sudo mkdir /data && sudo mount /dev/nvme1n1 /data
echo "UUID=$(sudo blkid -s UUID -o value /dev/nvme1n1) /data ext4 defaults,nofail 0 2" | sudo tee -a /etc/fstab
```

### 3.3 Software
Run `KnowledgeGraph/deploy/ec2/bootstrap.sh` (written, **not yet executed anywhere**). It installs: git, Python >= 3.11,
.NET SDK 8 (Roslyn extractor), Docker Engine + Compose plugin; creates `/data/neo4j/{data,logs,backups}` owned by uid 7474;
clones the repo; creates `.venv` with CPU-only torch and `pip install -e ".[dev]"`; copies the env templates; starts Neo4j;
installs the MCP systemd unit (not started).

### 3.4 GitHub access
1. Create a **read-only deploy key** for the repo, put it in `~/.ssh/`, add GitHub to `known_hosts`.
2. Test: `git ls-remote git@github.com:<org>/<repo>.git`.
3. For the PR stage (M6) create a second, narrowly scoped credential: a fine-grained token with **Contents: write on a
   `kg/*` branch prefix and Pull requests: write**, stored in Secrets Manager. The read-only deploy key is not reused for
   writes.

### 3.5 Neo4j container
`deploy/ec2/docker-compose.yml`: `neo4j:5.26-community`, `127.0.0.1:7474` and `127.0.0.1:7687` only, data and logs on
`/data/neo4j`, heap and page cache 4 GB each (tune later from real graph size).

1. Set the same `NEO4J_PASSWORD` in `deploy/ec2/.env` and `KnowledgeGraph/.env`.
2. The password is stored on **first start**. If it was started with a placeholder: `docker compose down`, wipe
   `/data/neo4j/data/*`, start again.
3. `docker compose ps` must show `healthy`.
4. Exit check: `cypher-shell` connects, and data survives `docker compose down/up` and a reboot.

### 3.4b Secrets
Neo4j password, `KG_MCP_TOKEN`, Anthropic key, PR token: Secrets Manager, injected into `.env` files (chmod 600) at start by
a small script, never committed. `kgpipe doctor` checks that all are present.

### 3.6 MCP service
```bash
sudo systemctl enable --now spectrum-kg-mcp
curl -i http://localhost:8765/mcp        # expect 401 without the token
```
First search downloads the ~1.2 GB Qwen model; pre-warm it once after install (`kgpipe doctor --warm-model`).

### 3.7 Network
Security group rule: TCP 8765 from the **VPN CIDR only**. No public exposure. Neo4j ports stay on localhost.
Client example: `claude mcp add --transport http spectrum-kg http://<private-ip>:8765/mcp --header "Authorization: Bearer <token>"`.

### 3.8 Backups
- `deploy/ec2/backup.sh`: stops Neo4j, `neo4j-admin database dump`, restarts, keeps 7 local dumps, optional S3 upload.
  Community edition cannot dump a running database, so there is ~1 minute of downtime. Schedule at night.
- EBS snapshot of `/data` after the first successful load and before every phase load.
- Test a restore once (`docker run ... neo4j-admin database load`) and record the procedure in `deploy/ec2/RESTORE.md`.

## 4. Baseline: rebuild phases 0 and 1 from Git (M2)

Phases 0 and 1 are **rebuilt from source**, not copied from Aura. The existing Aura graph is only the reference to compare
against. The curated functional YAML is **reused as is** (it is the expensive human work).

### 4.1 Prepare the repo
1. Commit `graphs-by-phase/phase-0/phase-0/<Form>/...` (4 forms) and `phase-1/phase-1/<Form>/...` (52 forms).
2. Commit the curated per-phase `KnowledgeGraph/domain/` for both phases and the merged `KnowledgeGraph/domain/`.
3. Commit `sp-export/` (full SP export) and `phases.yaml`.
4. Fix `kg.yaml`: `nested_sp_dirs` currently says `../embedding_text` but the folder is `nestedSP_embedding_text`; this
   is replaced by the new nested resolver in section 6, so do not patch it in isolation.
5. Remove `/graphs-by-phase` from `.gitignore`, push, tag the commit `baseline-p0p1`.

### 4.2 Build and load
1. `kgpipe fetch --commit baseline-p0p1` (clone at the tag).
2. `kg validate`. It must be clean. Known warnings (dangling SP-to-SP calls, SPs named in the data layer with no source,
   parameter mismatches) come from the code and are reported, not fixed (see `graphs-by-phase/README.md`).
3. `kg build` against the empty local Neo4j (full load is safe here because nothing exists to prune). Run inside `tmux`:
   embedding ~20k nodes with Qwen3-0.6B on 4 CPU cores has **not been timed** and could take hours. If too slow: copy the
   existing `.cache/` from the current machine (unchanged texts are reused), or run once on a temporary `g4dn.xlarge`.
4. Verify against Aura through MCP `describe_graph` and Cypher: ~20,178 nodes, matching counts per label and per edge type
   **except** the intended differences (Git paths and URLs). Record any other difference and explain it.
5. `pytest -m live` against the new Neo4j **[verify these tests work with a local database]**.
6. Run `backup.sh`, take an EBS snapshot, tag `KGMeta.commit` in the report.

Exit: local graph matches Aura, MCP answers a LAN client, restore tested.

## 6. Nested stored procedures (M5)

Replaces the manual prompt-based process (`prompt_nested_sps_from_winform_sp_folders.md`,
`prompt_document_missing_nested_sps.md`).

### 6.1 Inputs
- Bundle SPs: `.sql` under each bundle's `StoredProcedures/` (the baseline).
- `sp-export/`: full export, one `Schema.ProcName.sql` per SP, UTF-8, exactly as exported.
- Settings in `kg.yaml`:
```yaml
nested_sp:
  export_dirs: [../sp-export]
  max_depth: 8
  ignore: ["sp_*", "xp_*"]
```

### 6.2 New module `src/spectrum_kg/extract/nested.py`
1. Index `sp-export/` by lowercased `schema.name` (file name is authoritative; warn if the `CREATE PROCEDURE` name differs).
2. For each baseline SP, parse with sqlglot (comments stripped) and collect `EXEC` / `EXECUTE` targets, with optional
   `@var =`, one- to three-part names, with or without `[]`.
3. Resolve each target. Unqualified names resolve through the export index; if ambiguous or absent, report as unresolved.
4. Queue the targets that are not in the baseline, parse them, repeat until no new SPs or depth 8.
5. Record **dynamic** calls (`EXEC @var`, `EXEC(@sql)`) with the variable and its source if visible. Do not guess targets.
6. Output: the resolved set, plus a report `nested_sps_report.csv` (caller, depth, forms, phase, status:
   `resolved | not-in-export | dynamic | ambiguous | depth-cap`).

The same closure code is used by `kgpipe nested-sps` (report only) and by `build.py` (adds the SPs to the graph), so the
two cannot disagree.

### 6.3 `build.py` changes
- Replace the `nested_sp_dirs` `.txt` reader with the resolver above. Each resolved SP gets `bundles=["nested-sp"]`,
  `source_files=[<repo path in sp-export/>]` and its `source_url`.
- Keep reading `.txt` embedding-text files only behind a legacy flag (`nested_sp_dirs`), for a one-time migration. A
  bundle's own `.sql` still wins over a nested copy.
- Only **reachable** SPs are added. `kg validate` check 4 (every SP file reachable from a form) must keep passing; an SP in
  `sp-export/` that nothing reaches is never added.

### 6.4 One-time migration of the 197 existing files
1. For each `nestedSP_embedding_text/*.txt`, check whether `sp-export/` has the same SP.
2. If yes, compare the SQL after `Code:` with the export; list differences for a human.
3. If no, extract the SQL after `Code:` into `sp-export/` (only for SPs the export lacks), noting the source.
4. After the rebuild the nested set must equal the old one (same SP ids), apart from differences explained above.

### 6.5 What stays unresolved by design
15 stub SPs in the live graph are named in data-layer code but have no source; SP names built at runtime (`ODT<x>.ProcedureName`,
`<Tag>Save` of Single Field Master) are dynamic. They remain stubs/reports. `validate` flags any **rule** that cites an SP with
no source.

### 6.6 Tests
- Fixture SPs: direct call, 3-deep chain, cycle, system proc, `EXEC @v`, `EXEC(@sql)`, schema-less name, missing from export.
- Golden test: on the phase 0+1 baseline the resolver returns the 177 SPs listed in `missing_nested_sps_unique.csv`
  (minus any not in the export), **[verify the count against the real export]**.

## 7. Incremental update of the graph (M4)

`kg build` today is a full rebuild and load, and `prune` (`load.py`, `MATCH (n:Searchable) WHERE NOT n.id IN $ids DETACH DELETE n`)
deletes every node not in the graph passed in. A phase-only build would wipe the other phases. The pipeline therefore never
loads a partial graph.

### 7.1 Rules
1. Always build the **complete** in-memory graph from the **whole repo** at the pinned commit (all phases in `phases.yaml`).
   Roslyn and embedding caches make this cheap after the first run.
2. Load by **diff**, not by reload:
   - add `content_hash` to every node and edge (hash of props, excluding `embedding`);
   - read `id` + `content_hash` from Neo4j; write only new or changed nodes/edges; delete only ids that vanished;
   - delete and recompute all `derived=true` edges (`USES_TABLE`, `SHARES_TABLE`, `CALLS_SP`, `PERSISTED_IN`) on every load.
3. **Prune guard:** refuse to delete if the new graph has fewer than N% of the stored nodes (default 90%) or if any phase in
   `phases.yaml` produced zero bundles. Override only with `--force-prune` and an explicit reason in the log.
4. **Embeddings:** only nodes whose embedding-text hash changed are re-embedded. `load_graph` already receives
   `embedding_hashes` (`load.py:42`), so part of this exists **[verify behaviour]**.
5. **Atomic enough:** take a backup before every load; if verify fails (section 8.7), restore it automatically.

### 7.2 Acceptance tests
| Test | Expect |
|---|---|
| Re-run on the same commit | 0 node writes, 0 edge writes, 0 embeddings |
| Edit one method body | that method + dependent derived text change, nothing else |
| Edit an SP that writes a new table | new WRITES edge, new Table/Column nodes, derived edges updated for every form reaching it |
| Delete a form folder | its nodes vanish; shared nodes (QCGroup) survive while another copy exists |
| Incremental result vs full rebuild into a scratch database | identical (nightly drift check) |
| Partial input (one phase only) | guard refuses to prune |

## 8. The `kgpipe` tool (M5 and M6)

A Python package `src/kgpipe/` installed with the existing `pip install -e .`, exposing `kgpipe` (Typer, same style as `kg`).
Each stage is a separate command and `run` chains them. Stages communicate through files in a run directory
(`/data/kgpipe/runs/<run-id>/`), so any stage can be re-run alone and a failed run can resume.

### 8.1 Commands
| Command | Does |
|---|---|
| `kgpipe doctor` | checks tools (git, dotnet, docker, python), disk, Neo4j reachability, secrets, GitHub access, Anthropic key, model cache |
| `kgpipe fetch [--commit SHA]` | fetch/checkout the repo at a commit; export `KG_GIT_COMMIT`; record in run state |
| `kgpipe phases [--check]` | validate `phases.yaml`; compare with the folders on disk; list **new or changed forms** since the commit stored in `KGMeta` |
| `kgpipe parse` | Roslyn + sqlglot for the whole repo (cached) |
| `kgpipe nested-sps` | section 6: resolve nested SPs, write `nested_sps_report.csv`, fail on unresolved items that a rule cites |
| `kgpipe build-graph` | produce `graph.json` (full, in memory then dumped; no load) |
| `kgpipe gen-domain --phase N` | section 9: LLM-generate YAML for forms that have none; write to a `kg/phase-N-<run-id>` branch and open a PR |
| `kgpipe merge-domain` | regenerate merged `KnowledgeGraph/domain/` from per-phase sources |
| `kgpipe validate` | `kg validate` + extra checks (8.5) |
| `kgpipe embed` | build embedding texts, embed only changed ones |
| `kgpipe load [--dry-run]` | pre-load backup, diff-load, prune guard, `KGMeta` stamp |
| `kgpipe verify` | post-load checks and optional automatic rollback |
| `kgpipe run --phase N [--from STAGE] [--to STAGE]` | chain the stages, one lock, one log |
| `kgpipe backup` / `restore <dump>` | wrappers around `deploy/ec2/backup.sh` and its restore |
| `kgpipe status` | last run, graph commit vs repo head, node counts per phase |

### 8.2 `pipeline.yaml`
```yaml
repo: {url: git@github.com:<org>/<repo>.git, branch: main, checkout: /data/kgpipe/repo}
phases_file: phases.yaml
neo4j: {uri: bolt://localhost:7687, database: null}
embedding: {provider: local, model: Qwen/Qwen3-Embedding-0.6B, dims: 1024}
llm: {model: claude-sonnet-5-5, max_tokens: 8000, temperature: 0}
nested_sp: {export_dirs: [sp-export], max_depth: 8}
guards: {min_node_ratio: 0.9, backup_before_load: true, rollback_on_verify_fail: true}
review: {mode: pull_request, branch_prefix: "kg/", reviewers: []}
```

### 8.3 Run state and locking
- Lock file in `/data/kgpipe/lock`; a second run exits with a clear message.
- `run.json` per run: commit, phase, stage statuses, timings, counts, warnings, hashes of inputs. `kgpipe status` reads it.
- Logs to the run directory and CloudWatch.

### 8.4 Functional layer storage and merge
- Per-phase curated YAML under `graphs-by-phase/phase-N/phase-N/KnowledgeGraph/domain/` is the **source of truth**.
- The merged `KnowledgeGraph/domain/` is **derived**; `merge-domain` regenerates it. Today
  `scripts/merge_phase_domains.py` contains a hand-set `STEP_ORDER` for the processes that span phases 0 and 1.
  For new phases this must move to data (an `order:` per process step or a `process_order.yaml`) and the script must be
  generalised to N phases (it hard-codes D0 and D1).
- Merge rules stay as today: later phase wins for scalar text, lists are unioned (case-insensitive for SQL/VB names),
  steps renumbered.

### 8.5 Validation beyond `kg validate`
- every rule's `implemented_by` resolves to a node **with source** (not a stub);
- every new form and control has a doc and is governed by at least one rule and one process step;
- every `source_url` host and commit match `repo`/`KGMeta`;
- no process step references a form that is in no phase;
- nested SP report has no `unresolved` entry that a rule or concept depends on.

### 8.6 Verify
Node and edge counts per label (vs previous run and vs expectation), `KGMeta.commit` equals the loaded commit, `describe_graph`
works, five fixed smoke queries return non-empty (a form, a method, an SP, a table, a rule), and a sample of 20 `source_url`
values returns HTTP 200 from GitHub. On failure and `rollback_on_verify_fail`, restore the pre-load backup.

## 9. YAML generation stage (M6)

### 9.1 What is generated
For each **form and user control that has no `domain/forms/<name>.yaml`**, and for the phase's concepts, rules and process
steps. Existing curated files are **never overwritten**. Output shapes follow `GRAPH_STRUCTURE.md` section 5.1 and the
existing phase 0/1 YAML.

### 9.2 Grounding (what the model sees)
- from `graph.json`: the form's methods, controls, SP chain (including nested SPs), tables written/read, shared tables;
- the form's code excerpts with `file:line` and the permalink;
- the functional doc for the form if present (`documentations/`), otherwise none;
- 3-5 curated phase 0/1 YAML files as examples, selected by similar form kind (master / transaction / component);
- the module, concept and process catalog already in `domain/`, so new items reuse existing keys instead of duplicating.

### 9.3 Hard rules in the prompt and in code
1. Every business rule must cite evidence (`file:line` and method or SP id). Rules without a real citation are dropped.
2. Description text starts with an evidence line (`Evidence: code` or `Evidence: ... (inferred)`), as in the current YAML.
3. Messages are quoted exactly from code; nothing is invented.
4. Output is structured JSON validated against a schema, then rendered to YAML by code, never free text pasted into files.
5. A rule that merges several forms (uniqueness, mandatory fields, ...) updates the existing shared rule's `applies_to` list
   instead of creating a duplicate.

### 9.4 Review flow (PR)
1. Generated files are committed to branch `kg/phase-N-<run-id>` and a PR is opened with: the phase, the commit, the list of
   new/changed files, validation results, the nested SP report and a diff summary.
2. A human reviews and merges. **Merge is the approval.**
3. `kgpipe load` runs only from the merged `main` commit. Nothing generated reaches Neo4j unreviewed.

### 9.5 Quality gate before trusting it (do this first)
Regenerate phase 1's YAML into a scratch folder and compare with the curated version: keys, form-to-concept mapping, rule
count and citations, process step membership. Record precision (generated items that exist in curated) and recall (curated
items that were generated). Proceed to phase 2 only when both are acceptable to you; the thresholds are yours to set. If
quality is low, switch the generator to a hybrid mode (deterministic for forms, controls and method notes; LLM only for
concepts, rules and processes).

### 9.6 Cost and repeatability
Temperature 0, prompt and model version recorded in `run.json`. Estimate the token cost on one phase 1 form before running a
full phase.

## 10. Runbook: adding a new phase (the thing this plan is for)

Prerequisite: M1-M6 done. Example: phase 2.

1. **Commit the code.** Add `graphs-by-phase/phase-2/phase-2/<Form>/...` bundles (same shape as phase 1). If the full SP export
   changed, update `sp-export/`. Push to `main`.
2. **Declare the phase.** Add `phases: 2:` with its forms to `phases.yaml`. Push.
3. **On EC2:** `kgpipe doctor`, then `kgpipe run --phase 2 --to gen-domain`.
   This fetches the commit, parses, resolves nested SPs, builds the graph, generates YAML for the new forms and opens a PR.
4. **Review the PR:** read the nested SP report (unresolved, dynamic, missing from export), the generated forms, concepts,
   rules and process steps. Edit in the PR branch where needed. Merge.
5. **Load:** `kgpipe run --phase 2 --from merge-domain`. This merges the domain layer, validates, embeds only changed text,
   takes a backup, diff-loads, and verifies.
6. **Check:** `kgpipe status` shows the new commit and counts; ask MCP a question about a phase 2 form; open one `source_url`.
7. **If something is wrong:** `kgpipe restore <dump>` (or the automatic rollback already did), fix the repo, rerun.

Changing code in an **existing** phase uses the same flow without step 2 and without YAML generation (existing curated YAML
is untouched); only the technical layer and the affected embeddings change.

## 11. Security and operations

| Topic | Rule |
|---|---|
| Exposure | Only 8765 from the VPN CIDR. Neo4j on localhost only. SSH from admin IP or SSM. |
| Secrets | Secrets Manager; `.env` chmod 600; never in the repo; separate read-only and PR-write GitHub credentials. |

| Backups | Nightly dump to S3, EBS snapshots, restore tested after M2 and after M4. |
| Monitoring | CloudWatch for service up, disk usage on `/data`, Neo4j memory, last successful run age, `KGMeta.commit` lag vs repo head. |
| Patching | Pin the Neo4j image tag and the Python dependency set; upgrade through a rebuild into a scratch database first. |
| Embedding model | Never change it in place; a change means re-embedding everything and a new `KGMeta.embedding_model`. |

## 13. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| CPU embedding time for the first load is unknown | M2 takes hours or a day | copy `.cache/`; temporary GPU instance; time a 500-node sample first |
| Partial graph loaded with prune enabled | data loss | M4 prune guard + pre-load backup + rollback |
| LLM-generated rules are wrong or uncited | bad curated layer | evidence-required rule, schema validation, PR review, phase 1 regression test |
| Source code leaves the company boundary to the LLM API | policy breach | confirm policy before enabling `gen-domain`; the stage is optional |
| SP export is incomplete or out of date | nested SPs missing | report `not-in-export`; block load when a rule depends on one |
| Dynamic SQL hides SPs/tables | graph gaps | reported, never guessed; documented known limit |
| Folder layout changes later | all stored links break | freeze layout; `repo.root` + path mapping in config |
| Line anchors drift after edits | wrong lines | permalinks pinned to a SHA; every load restamps the commit |
| Hand-set `STEP_ORDER` in the merge script | wrong process order for new phases | move to data in M6 |
| `kg build` assumes Windows paths in places | Linux build breaks | already fixed for the Roslyn extractor name (`config.py`); run the offline tests on Linux in M2 |
| Docker Neo4j data corruption on abrupt stop | outage | EBS + dump backups; clean shutdown in the systemd/compose config |
| Large files in Git | slow clones | keep `graph.json`, html, zips out; consider Git LFS only if bundles are large |
